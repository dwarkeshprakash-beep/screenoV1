## SECURITY_AGENT Report

### Critical (fix before next commit)
- **Exam routes have zero authentication — any anonymous HTTP client can GET exam questions or POST answers** | `backend/src/routes/exam.routes.js:1-41` | The exam router is mounted at `/api/exam` with no `authMiddleware` call anywhere in the file or in `server.js` before it; possession of any valid (or guessable) token string is the only gate, and the token is never marked single-use until `submitExam` checks `interview.status`, so a race-condition replay is possible.
- **Magic-link `validateMagicLink` never marks the token consumed** | `backend/src/services/auth.service.js:128-145` | After issuing a `sessionToken`, the raw token hash in the DB is never cleared or invalidated; any attacker who intercepts or obtains the URL can call `POST /api/auth/magic-link/:token` repeatedly to mint fresh 4-hour candidate JWTs without limit.
- **In-memory rate limiter is per-process and resets on every server restart** | `backend/src/middleware/rate-limit.js:4-32` | The `hits` Map lives only in memory: every server restart wipes it, and if Node is clustered the counters are siloed per worker — the 30-attempt window on `/api/auth/login` disappears after any restart.

### High (fix this sprint)
- **`GET /api/schedule/slots/:token` is fully public with no validation or ownership check** | `backend/src/routes/schedule.routes.js:12-20` | Any caller that can guess or enumerate a scheduling token can retrieve availability data for any manager.
- **`assertInterviewScope` short-circuits when `identity.interviewId` is null** | `backend/src/services/candidate-identity.service.js:12-16` | Internal candidates who log in via the dashboard get a JWT with no `interviewId`, so the guard is silently skipped; they can call `POST /api/interviews/<other_id>/start|answer|complete` for other candidates' interviews.
- **`developmentFallback` is a client-controlled flag accepted in production** | `backend/src/routes/interview.routes.js:39` | If `NODE_ENV` is not set, a candidate can skip transcription entirely by sending `developmentFallback: true`.
- **Refresh-token rotation has no theft detection** | `backend/src/services/auth.service.js:92-116` | A stolen refresh token used before the legitimate user goes undetected.
- **`secure: process.env.NODE_ENV === 'production'` on refresh cookie** | `backend/src/routes/auth.routes.js:14` | Cookie sent over plain HTTP in non-production environments including staging.
- **CORS wildcard allows any origin in non-production** | `backend/server.js:38` | All cross-origin credentialed requests accepted in dev/staging.

### Medium (tech debt)
- `getByIdWithPassword` uses `SELECT *` which selects the password hash | user.repository.js
- `bulkUpsert` pushes raw `err.message` (may include DB column/constraint names) to client
- No `Content-Security-Policy` header set anywhere | server.js
- `GET /api/reports/candidate/:userId` has no company-scope check on `userId` | report.routes.js
- `questionText` from client accepted as question-lookup fallback | interview.service.js:67-74

### What's good
- Refresh tokens hashed with SHA-256 before storage and rotated on every use — correct token hygiene
- Transcript/answer routes strip `answer` fields from questions returned to candidates — correct data minimisation

### Top recommendation
Invalidate (nullify) the magic-link token hash in the database immediately after first successful validation so each link is truly single-use.
